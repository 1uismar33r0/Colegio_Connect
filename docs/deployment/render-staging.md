## Intended request and process path

Browser → Render HTTPS → Spring Boot on `$PORT` → private PostgreSQL 18. Vite compiles React once; Spring serves the assets and routes `/api` separately. Spring Security retains server sessions, a Secure/HttpOnly/SameSite=Lax session cookie, and the existing XSRF-TOKEN/X-XSRF-TOKEN flow. Render's proxy headers are interpreted by the staging profile. Mailpit SMTP and UI bind only to `127.0.0.1` inside the web container; no public Mailpit route or port is configured.

`backend/Dockerfile` and `compose.yaml` remain the local development path. The root `Dockerfile.render` builds both applications and includes the Mailpit binary. It does not run a Node development server at runtime. `application-render-staging.properties` binds Spring to the Render port, enables a small Hikari pool, exposes status-only health/readiness checks, turns off public Swagger/OpenAPI, and disables registration/resend by default. Local Compose uses the default profile and retains its registration flow. The image uses a non-root user and `tini`; the entrypoint stops both Java and Mailpit on SIGTERM or if either child exits unexpectedly.

## Public access boundary

The public React shell and known browser routes may load anonymously; React handles navigation and Spring still guards every `/api` business route. `/actuator/health` and `/actuator/health/readiness` return status only. API/admin routes, verification codes, Mailpit UI/API/SMTP, database credentials and logs are not published. Remote registration remains **blocked** until Resend delivery is demonstrated and registration is explicitly enabled. Without a verified domain, the Resend sandbox sender may deliver only to the Resend account address; set `APP_REGISTRATION_ALLOWED_EMAIL` to that same address before enabling registration. No code is returned through the public application and verification is not bypassed.

## Blueprint and environment inventory

The proposed [`render.yaml`](../../render.yaml) defines `colegio-connect` as a Free Docker web service in Oregon, built from `main` with `Dockerfile.render` and root context. Automatic deploys and preview environments are off. `/actuator/health/readiness` is the health path. `colegio-connect-db` is a separate Free PostgreSQL 18 database in Oregon, with public IP access disabled. The Blueprint uses `fromDatabase` references; it must be validated in the authorized Render account before applying. The existing PurpleGlass resources are unrelated. The proposed Blueprint does not create them, reuse them, or affect them.

Node 24 and Java 25 are build-image versions, not runtime environment variables. `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` and `SPRING_DATASOURCE_PASSWORD` are set by the entrypoint after parsing the private Render database reference. Never paste a populated connection URL or credentials into Git, PR comments, logs or the report. The startup path is `tini` → entrypoint → loopback Mailpit plus Spring Boot; Spring serves the built Vite files and relative `/api` on the same origin. Render terminates HTTPS and forwards trusted request headers; the staging Spring profile interprets those headers while the existing Secure/HttpOnly/SameSite=Lax session cookie and CSRF header flow remain in force.

**Portless URI fix:** `DATABASE_URL` must be the complete private `postgresql://` or `postgres://` URI, not a hostname or JDBC URL. Its authority may include `:port`; if omitted, the entrypoint uses PostgreSQL's default 5432. `DB_NAME` must match the URI database path, while `DB_USER` and `DB_PASSWORD` remain separately supplied variables. Encode reserved characters in the URI's userinfo; the entrypoint does not parse/decode credential values and never logs them. The URL parser rejects missing/invalid scheme, host, explicit port or database with an error containing no values. **No Render variable changes are needed** for a valid private URI and matching database references. If the next deploy reports a database mismatch, verify the four variables' *sources* in the service dashboard without copying their values. The live secret values were not available through the connected read-only service metadata.

**Hosted verification mail:** Put a new sending-only API key directly into the existing Colegio web service's Render Environment as `RESEND_API_KEY`; set `APP_MAIL_PROVIDER=resend`. For a single-account sandbox trial, set `APP_MAIL_FROM=onboarding@resend.dev` and `APP_REGISTRATION_ALLOWED_EMAIL` to the Resend account's `@upr.edu` address. This sender cannot deliver to teammates or other users. The app refuses to start with the sandbox sender unless the allowlist is set. Deploy the new image with registration still disabled, confirm readiness, then set `APP_REGISTRATION_ENABLED=true` for a controlled real signup and verify that the code arrives privately. Leave it enabled only if that flow succeeds. For general registration, verify a domain you control, use a sender on that domain and remove the allowlist. The registration service commits the account before email delivery; a failed send is logged without the code and recovered through **Resend code** after its cooldown. The HTTPS sender does not print response bodies, credentials, addresses or codes. New verified accounts have no application roles until an administrator assigns an appropriate role. Moderator access must never be granted automatically to public signups.

## Reproduce local verification

Use a clean isolated Docker network and synthetic PostgreSQL 18 database; do not reuse a developer database or existing Compose services. Build with `docker build -f Dockerfile.render -t colegio-connect:render-staging-local .`. Run the web image with `--memory 512m --cpus 0.1`, and a separate PostgreSQL 18 container with `--memory 256m --cpus 0.1`. Publish only the web port to host loopback (for example `127.0.0.1:18084:10000`). Supply `DATABASE_URL`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, and **local only** `DB_SSLMODE=disable` from disposable synthetic test values. Wait for `/actuator/health/readiness` to return 200; the local Free-sized cold start took about 130 seconds. Run `node infra/render/smoke.mjs http://127.0.0.1:18084`. The script checks the default disabled-registration boundary and current role routes. For a private synthetic mail-flow test only, start a second disposable app with `APP_REGISTRATION_ENABLED=true` on another loopback port and run `node infra/render/synthetic-mail-smoke.mjs http://127.0.0.1:<test-port> <temporary-app-container>`; this script reads Mailpit through `docker exec`, does not print the code, and refuses non-loopback URLs. Never target a public service. Remove only the containers/network created for this test when finished. See TE-16 for actual results and exact revision.

An optional browser check uses a temporary `playwright-core` installation and locally installed Chrome. Set `PLAYWRIGHT_CORE_DIR` to that scratch package directory and `CHROME_PATH` to Chrome's executable, then run `node infra/render/browser-smoke.cjs http://127.0.0.1:18084`. The script rejects non-loopback URLs and checks signed-out loading, assets, and the protected-route redirect. With a **synthetic verified local account assigned the STUDENT role**, `SYNTHETIC_EMAIL` and `SYNTHETIC_PASSWORD` enable login, refresh/session, student page and 375px overflow checks. New registrations have no role; assign the role only in the disposable test database or through the reviewed administrator workflow. These variables and browser profiles must stay out of Git. For team manual acceptance on an authorized hosted URL, use a signed-out browser to check `/`, `/login`, `/student`, `/institution`, `/company`, `/moderation`, refresh and mobile width; verify that protected pages redirect to sign-in, assets load without console errors, and registration remains unavailable. A reviewed synthetic test account and safe email workflow are needed before hosted login/session testing.

## Troubleshooting, rollback and continuity

- If startup fails, inspect sanitized service logs, profile, port, database-reference presence and Flyway failure. Do not copy credential-bearing URLs into reports. A slow Free cold start is expected in the local 0.1 CPU trial; measure Render's actual health timeout before acceptance.
- If readiness is 503, check the private database and migration status. Basic process liveness does not prove database readiness. Reconnection was observed locally; hosted behavior remains unverified.
- If SPA routes show 401/404, confirm the combined image contains `static/index.html` and built assets, and that the requested path is an explicit browser route. API failures must remain JSON/401/403 rather than SPA HTML.
- If mail is absent, check loopback SMTP and Mailpit process inside a controlled local test. Mailpit's `/tmp` storage is ephemeral. Never expose its UI/API or switch on public registration as a troubleshooting shortcut.
- Roll back the web service only to a reviewed image compatible with the *current* Flyway schema. Flyway migrations are forward-only here; app rollback does not reverse them. With Free PostgreSQL, no managed backup or durable recovery guarantee exists. Test export/import to a fresh isolated database before relying on it for the final demo. The Free database expires after 30 days and the shared web hours can be exhausted by other Free services in the same workspace.
