## Gabriel's backend contribution

Commit `d43afff1fc2660b8cc5191401c669caaa6084eaf` adds `CompanyDecisionController.decide`, `CompanyDecisionService.decide`, and `CompanyDecisionRequest`. `POST /api/admin/organizations/{id}/decision` accepts `APPROVED` or `REJECTED`; rejection requires a nonblank reason of at most 500 characters, and an optional approval reason is also bounded. A V5 migration adds `organizations.decision_reason`; the reason stays out of the minimal audit row. `OrganizationRepository.findByIdForUpdate` locks the target row. Only a pending `EXTERNAL_COMPANY` can transition; missing IDs return 404, other organization types or invalid input return 400, and any repeated or conflicting decision returns 409.

A request passes Spring session authentication and CSRF, then `@authz.canModerate(authentication)` rechecks the actor's active account and persisted global `MODERATOR` role. The controller derives the actor UUID from that server-side authentication. The service locks the company, changes its status and reason, and calls `AuditService.record` with `ORGANIZATION_APPROVED` or `ORGANIZATION_REJECTED`, target type `ORGANIZATION`, and the actual organization ID. Both changes share the service's transaction; the audit service generates the event time. If the audit call throws, the company state rolls back too. Concurrent requests serialize on the row lock, leaving one decision and one audit row.

The implementation uses Gabriel's Issue #15 audit service and Massini's merged authorization policy. Test fixtures create pending companies and moderator accounts; they are not production registration or role-management workflows.

## Pending-company queue backend

Gabriel's local commit `fcd9224436b1454d5cf34629bdb306c05188988d` adds `PendingCompanyQueueController.findPending`, `PendingCompanyQueueService.findPending`, `OrganizationRepository.findByOrgTypeAndApprovalStatus`, `PendingCompanyResponse`, `PendingCompanyPageResponse`, and `PendingCompanyQueueIntegrationTest`. It is based on reviewed decision-branch head `2b4ca24b493bc2b5920d294a32b8520fa131b4f9`; no #115 notification or #118 harness commits were imported. No schema migration or audit write was added for this read operation.

Luis's future moderator review screen can call `GET /api/admin/organizations/pending?page=0&size=20`. The endpoint uses the existing `@authz.canModerate(authentication)` policy, which requires an authenticated active account and a current persisted global moderator assignment. The database query selects only `EXTERNAL_COMPANY` rows in `PENDING` and pages them before mapping. Each item contains exactly `id`, `name`, and `approvalStatus`; the envelope contains `items`, `page`, `size`, `totalElements`, and `totalPages`. Defaults are page 0 and size 20; size 1–100 is accepted, negative page or out-of-range size returns 400. Results sort by name ascending, then unique organization ID ascending. These bounds and ordering are implementation choices following the audit endpoint convention, not proposal requirements or a claim of chronological order.

A moderator can pass an item's `id` to the existing `POST /api/admin/organizations/{id}/decision` with valid session authentication and CSRF. The request-level integration test retrieved a synthetic pending company, approved it through the real decision endpoint, retrieved an empty queue, then verified its committed `APPROVED` state and one `ORGANIZATION_APPROVED` audit row with the actual actor, target, and server time. Loading the queue itself created no audit row and changed no company state. Test fixtures do not establish production company registration, and stable ordering does not guarantee a snapshot while other requests change the dataset.
